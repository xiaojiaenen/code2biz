# 业务域拆分（微服务/多仓库场景）

微服务项目最大的风险不是"分析不动"，是**没有域边界的情况下把所有东西拍平成一份文档**，结果读者打开一份几百个实体的大杂烩，比没有文档更难读。这份参考文档解决"要不要拆、怎么拆、拆完怎么在同一个 HTML 里呈现"。

## 第一步：域边界从哪来，不要让模型自己拍脑袋定

优先级：
1. **仓库/服务边界**：微服务场景下，一个服务通常就是一个域的强信号（尤其服务名本身就是域名，比如 `order-service`、`inventory-service`）——但不要无脑套用，有些"拆分"是技术边界（比如按性能/团队拆分的服务）不是业务边界，两个服务可能同属一个业务域
2. **用户已有的认知**：如果用户在任务开始时就说了"这几个服务算交易域，那几个算库存域"，以用户说法为准，不要用代码信号覆盖
3. **代码信号兜底**（前两者都没有时）：包名/模块名的共同前缀、数据库共享情况（多个服务是否读写同一批表，通常意味着同域或强耦合）、Phase 3 架构依赖图里的强连通分量（互相调用频繁的服务群大概率是同域）

**遇到域边界不确定的情况，直接问用户，不要沉默地自己判断。** 域划分错了，后面所有章节的分类、导航、图的聚类全部要返工，这是最不值得"模型自主判断"的一环。

## 第二步：每个提取出的事实都要打域标签

Phase 1 提取阶段（`references/01-extraction.md`）产出的每一条结构化数据——实体、状态机、规则、术语条目、依赖图节点——都要带上 `domain` 字段。这不是额外的工作，是在提取阶段就该做的事，不要等到 Phase 2 整合时再回头补标签（那时候上下文已经丢了，容易贴错）。

跨域的实体/流程（比如订单实体同时被交易域和物流域引用）不要强行归到单一域，标注 `domains: [交易域, 物流域]`，并且在术语表里重点体现——这正是痛点十"同一个东西不同部门叫法不同"的具体案例。

## 第三步：单文件 HTML 里怎么呈现域拆分

在 `references/07-single-html-packaging.md` 的左侧导航基础上，加一层域筛选：

- 导航顶部放一个域切换器（下拉或 tab），选中某个域后，右侧所有章节（领域模型/流程/规则/架构图）自动过滤成只显示该域相关的内容
- "全部"视图默认展示跨域主线（比如"订单到现金"全链路）+ 域清单，不展示每个域的全部细节，避免打开就是信息过载
- 架构图（Phase 3）按域上色/聚类，域切换器联动图的高亮，而不是两套独立的过滤逻辑
- 术语表是全局的，不随域筛选消失——因为它的核心价值恰恰是"让你看到同一个概念在不同域的叫法"，筛掉了就失去意义

## 什么时候不需要拆域

单体应用、或者虽然是微服务但业务边界本身就很清晰单一（比如一个服务就是完整的一个域，没有交叉引用）——这种情况硬拆反而增加导航负担。判断标准：如果术语提取阶段发现"跨域同义词"数量很少、架构依赖图里服务间调用也很稀疏，直接做成单一视图即可，不必强行套用域切换器 UI。
