# 整体架构 + 流程拆解规范（R5 / R6 / R7 集中实现）

> 这份参考是 SKILL.md 里 R5（流程五维度）、R6（架构拆解五问）、R7（图谱节点标准化标注）的集中落地文档。R3 业务优先 70/30 在 `02-synthesis-checklist.md` 里有写，本文件专注于结构化拆解。

## 1. 整体架构拆解 —— 五问（R6）

整体架构章节是新人"看懂这个系统是怎么搭的"的主入口。**这五问必须全部答出**，不能跳过——跳过任何一问都会让新人对系统的认知留个空洞，后面读流程、读规则时都得回头补。

### 1.1 架构拓扑

**要交付的内容**：

- **分层架构**：表现层（Web / Mobile / OpenAPI） / 业务层（应用服务 / 领域服务） / 数据层（DB / Cache / MQ） / 基础设施层（部署 / 监控 / 日志），每层在当前项目里的具体实现
- **模块架构**：核心模块清单（按域或按子系统组织），每个模块的边界（哪些能力归这个模块、哪些不属于）
- **服务架构**（如果是微服务）：服务清单 + 通信方式（同步 HTTP / 异步 MQ / 事件总线）+ 服务发现 / 注册中心
- **单体 vs 微服务 vs 组件化**的明确判断（不要暧昧），并说明判断依据

**配图**：一张顶层 `architecture` 图（archify 渲染），节点按层 / 按域聚类，配 R7 业务化标注。

**反例**：只输出一张图，节点是 `Web → Service A → Service B → DB`，下面写"本系统采用分层架构"——空洞，没有回答拓扑。
**正例**：文字先说"本系统是单体 FastAPI 应用，按职责纵向切分为 6 个 API 子模块 + 5 个核心服务模块 + 3 个数据访问模块"；然后给图，节点精确到子模块并配 R7 标注。

### 1.2 设计目的（为什么这么设计）

**要回答的不是"是什么"而是"为什么"**——这套架构为什么存在？它当初被选中是为了解决什么具体的业务/技术问题？

- **业务体量**：日活 / 日订单 / 日交易额 / 数据增长曲线（取代码里能查到的实际数字，不要凭印象）
- **迭代节奏**：版本发布频率（git log 看）、特性上线速度需求
- **性能诉求**：QPS 上限、P99 延迟要求、并发用户数
- **组织结构**（康威定律）：团队规模、跨团队协作模式、是不是因为某个团队/历史原因导致现在的形状

**怎么找这些信息**：
- 业务体量 / 性能诉求：日志、监控配置、容量规划文档；如果没有，**明确写"项目里未找到相关线索，疑似初版设计未考虑大规模，但现状仍是单体"**
- 迭代节奏：`git log --since`、`git shortlog -s` 统计
- 组织结构：问用户（如果用户是当事人或能联系到当事人），或者在产物里标注"待确认"

**反例**：只说"因为业务发展需要"——空话。
**正例**："初版 2022 年上线时是单体 FastAPI，因为当时只有 1 个后端 + 1 个前端，且业务体量在千级订单/天，单体 + 异步任务足够应对；2023 年因合规要求加了一整套授权校验中间件（core/license_manager），目前仍是单体但已有拆分的预案（`docs/split-plan.md`，待确认有效性）"。

### 1.3 各层 / 各模块职责

**每个层、每个核心模块都必须有职责说明**——不是"用户服务负责用户"这种废话，而是说清楚这个模块承载哪些业务能力、为谁服务、典型调用方是谁。

**模板**：

```
### 部署执行器（core/deploy_executor.py）
- **业务能力**：接收部署任务、按 step 顺序执行 playbook、汇总每个 step 的成功/失败、判定任务终态
- **典型调用方**：api/deploy.py:execute_deploy、api/deploy.py:retry_step
- **依赖资源**：Ansible Runner（run_playbook_async）、DB（deploy_tasks / deploy_steps）
- **业务约束**：全局并发上限 2、单步超时 3600s、失败 break 后续 step
```

### 1.4 模块依赖关系

- **同步调用**：哪个模块 HTTP / RPC 调哪个
- **异步消息**：哪个模块订阅哪个 topic / queue
- **共享数据**：哪些表被多个模块读写、读写模式
- **依赖方向**（用 codegraph `callers`/`callees` 交叉校验，R2）

**配图**：archify `architecture` 图，节点按模块名 + R7 标注；边按调用方向画，颜色按依赖类型（同步 / 异步 / 共享数据）区分。

**反例**：只说"模块之间通过 HTTP 调用"——没说清谁调谁、为什么这么调。
**正例**：同步调用 `api/deploy.py:execute_deploy → core/deploy_executor.py:start_deploy`（每次新建部署任务，阻塞主流程返回 task_id，task_id 用于后续查状态）；异步消息 `core/deploy_executor.py 通过 WebSocket /api/deploy/{id}/log 推送 step 执行事件`（前端订阅做实时日志展示）。

### 1.5 架构优势、现存问题、业务适配性

**这是新人判断"这个系统还能扛多久 / 哪里会成为下一个事故的起点"的关键**——必须诚实写，不要粉饰。

- **架构优势**：哪些业务场景跑得好、为什么跑得好（异步削峰 / 缓存层 / 分库分表 / 读写分离等具体技术决策带来的具体业务收益）
- **现存问题**：哪些地方已经吃力（具体表现 + 原因）——比如"部署任务表 deploy_tasks 全量查询在 10w+ 任务时变慢，因为缺少 plan_id 上的索引"
- **业务适配性**：未来业务扩张时哪里会成为瓶颈——"如果订单量从 1k/天 涨到 100k/天，部署任务表的查询会成为瓶颈，需要按时间分区"

## 2. 核心流程拆解 —— 五维度（R5）

每条核心流程（部署主链路、下单链路、审批链路、对账链路、激活链路等）**必须覆盖五个维度**。这五个维度缺一不可——只写主流程而漏异常流程是 SKILL 要解决的核心痛点之一。

### 2.1 主流程（happy path）

**完整步骤，每一步含**：业务动作、状态从什么变成什么、触发的副作用（DB 写、MQ 发、缓存更新、第三方调用）。

**反例**："下单 → 支付 → 发货"三个词。
**正例**：

1. 用户点击"立即下单" → 前端 POST /api/orders，含商品列表、收货地址、优惠券
2. api/orders.py:create_order → 校验库存、计算价格、生成订单号 → 写 orders 表（status=pending_payment）→ 返回订单号和支付链接
3. 用户完成支付（异步回调 /api/payments/callback） → 支付服务 POST /api/orders/{id}/pay → 校验金额 → 改 status=paid，发消息到 MQ（topic=order_paid）
4. 库存服务订阅 order_paid → 扣减库存 → 发 order_fulfilled 消息
5. 履约服务订阅 order_fulfilled → 创建发货单 → 改 status=shipped

**每一步的前置条件 / 后置条件**也要写。

### 2.2 分支流程

**按业务条件 / 用户身份 / 场景分的分支**：

- VIP 用户：跳过某些校验、走快速通道
- 测试环境：跳过实名 / 跳过支付
- 灰度开关：新老逻辑双跑，按用户 ID 哈希分桶
- 不同来源订单（小程序 / H5 / 第三方平台）的差异处理
- 不同业务模式（B2B / B2C / 内部测试）的分支

**每个分支的"业务意义"必须说清**——不只是说"分支 A 走 X 逻辑"，要说"分支 A 是因为合规要求；分支 B 是因为运营活动期间的特殊处理"。

### 2.3 异常流程（关键中的关键）

**硬要求**：Phase 1 状态迁移表里有几条异常路径，文档里必须体现全部。

**异常维度**：

- **业务异常**：库存不足、余额不够、订单已取消、用户无权限
- **技术异常**：DB 超时、Redis 击穿、MQ 重试上限、第三方 API 5xx
- **并发异常**：乐观锁冲突、分布式锁竞争、幂等击穿
- **数据异常**：数据为空、字段缺失、格式不对、版本不匹配
- **网络异常**：断网、超时、半开连接、TLS 握手失败

**每条异常都要说**：触发条件 → 兜底逻辑 → 业务后果（数据回退到哪、用户看到什么、是否通知运营、是否触发人工介入）。

**反例**："如果失败则报错"。
**正例**："如果 Redis 击穿（命中 `cache_miss` 计数器且 QPS > 1000）→ 回源 DB → DB 走读副本 → 仍超时则降级返回本地 LRU 缓存（已降级 5min 标记）→ 同步发告警到 Sentry"。

### 2.4 数据流转流程

**这条流程涉及的数据从产生到消亡的全生命周期**：

- **产生**：哪个事件 / 哪个用户动作生成数据
- **加工**：经过哪些服务、哪些计算、哪些清洗
- **传输**：走 HTTP / MQ / 文件 / 实时流
- **存储**：哪些库哪些表、是否分库分表、是否有冷热分层
- **更新**：被哪些服务更新、并发写怎么处理、是否有版本号 / 乐观锁
- **删除 / 归档**：何时删、归档策略是什么、软删还是硬删

**反例**：只说"订单数据存在 orders 表"。
**正例**："订单数据产生于 `POST /api/orders`，写入主库 `orders_master.orders`（按用户 ID 哈希分 4 库）→ 通过 Canal 同步到 ES `orders_v1` 索引（用于列表查询）→ 30 天后归档到 `orders_archive`（按年分区）→ 90 天后清理（合规要求）→ 整个生命周期里订单状态字段被 6 个服务更新（订单、支付、库存、履约、退款、风控），使用 `version` 字段做乐观锁"。

### 2.5 权限 / 风控流程

**不是"调了 check_permission"就完事**——要说清**为什么这里需要校验、校验什么业务规则、失败业务后果**。

- **哪些业务节点需要权限校验**：操作人是不是本人 / 是不是该租户成员 / 是不是该角色
- **哪些场景有风控拦截**：异地登录 / 频繁下单 / 大额支付 / 异常时段
- **拦截后的业务后果**：直接拒绝 / 触发人工审核 / 限流 / 降级到简化流程 / 标记观察
- **为什么这么设计**：合规要求 / 防盗损 / 反作弊 / 用户体验权衡

**反例**："删除前调用 check_permission"。
**正例**："删除订单前调用 `Permission.can_delete_order(user, order)`，业务约束：仅订单创建者本人 + 订单状态为『待支付』时允许删除（防止误删已支付订单触发退款纠纷）；管理员角色绕过这个检查但需要写审计日志 `audit_order_deletion`"。

## 3. 图谱节点标准化标注（R7）

archify / codegraph 产出的每个节点、每条边都必须附**业务化标注**，不是只贴一个代号。这是把"画一张图"升级成"业务解读"的关键。

### 3.1 节点标注规范

| 维度 | 含义 | 格式 | 数据来源 |
|---|---|---|---|
| **代码位置** | 模块/类/函数 + 文件:行 | `core/deploy_executor.py:start_deploy` | codegraph `candidates` |
| **业务含义** | 这个节点在业务里是什么角色 | 短句（10-25 字） | Phase 1 + Phase 2 |
| **上下游依赖** | 被谁依赖、依赖谁 | `← api/deploy.py:execute_deploy` / `→ AnsibleRunner` | codegraph `callers`/`callees` |
| **触发条件** | 什么事件触发 | `POST /api/deploy` | Phase 1 入口点 + 状态迁移 |
| **输出结果** | 成功 / 失败后产出 | `task_id / status=running` | Phase 1 状态迁移 + 异常路径 |
| **对应异常场景** | 异常 / 补偿 / 降级 | `no hosts matched → failed` | Phase 1 异常路径 + pending.json |

**实现**：archify spec 的节点 `metadata` 字段（`sublabel` / `context` / `tag`），渲染时作为 native `<title>` 显示，hover 即可见。

### 3.2 边的标注

- 边本身按调用方向画
- 边类型（同步 HTTP / 异步 MQ / 共享 DB）通过颜色或 `metadata.kind` 区分
- 关键边附加条件（"仅在 status=running 时"）和频次（"每分钟 ~10 次"）

### 3.3 图下方必须配业务解读

每张图下方必须有"业务解读"小节（200-400 字），把图里每个域 / 模块用一段话讲清楚业务定位、典型场景、异常处理。**不能只输出图谱不做文字解读**。

**反例**（图谱 + 业务解读脱节）：输出一张干净的依赖图，节点用模块名标注，下方只写一句"如图所示为本系统架构"——这与"画一张图然后让读者自己悟"无异。

**正例**：同样一张图，节点 hover 出"部署执行器（core/deploy_executor.py:start_deploy）· 触发：POST /api/deploy · 失败处理：no hosts matched 视为失败 · 状态迁移：pending→running→success/partial/failed"，下方配套 200-400 字的"部署执行器业务解读"段落。

### 3.4 节点标注的代码化生成

`scripts/biz-*-to-archify.mjs` 在转 archify spec 时，应该把 codegraph + Phase 1 数据按上表格式填入节点的 `metadata`。如果某个节点的某个字段填不出，必须在产物里标注"待补"——而不是省略字段让图自己"看上去对"。
