# 业务深度解读：状态业务化 / 流程四层拆解 / 企业级业务解读（R12 / R13）

> 这份文档解决一个被 Russh 实测暴露的层级问题：上一轮门禁（R9-R11）解决的是
> "写没写、够不够长"，这一轮解决的是"**写的东西有没有业务含义**"。
> 实测产物里 6 台状态机的交付形态是 `unknown → running` 这种字面量流转，
> 15 处触发条件是"（同上触发，未单列）"——每个字都对，连起来等于什么都没讲。
> 状态名不是业务，方法名不是流程，枚举字面量照抄进文档就是技术噪声。

---

## 1. R12 · 状态流转业务化

**规则表述**：状态机在文档里的交付单位是"业务动作"，不是"状态字面量"。
每一个状态必须有业务定义，每一条迁移必须能回答三个问题：**这个流转对应什么真实业务动作？
是谁/什么触发的？流转完成在业务上意味着什么？** 禁止把枚举定义或方法名直接当作状态讲解。
落地标记由 `check-content-depth.mjs`（R9-7）机器检查。

### 1.1 为什么 "unknown → running" 是不合格的

反例（实测产物原文）：

> `unknown → running`（同上触发，未单列）

读者能从这行字里获得的信息量为零：

- `unknown` 是什么业务状态？不知道。是"已创建未调度"？是"数据迁移残留"？还是解析失败兜底？
- `running` 是"谁"在跑？人工点了一次执行，还是调度器自动认领？
- 为什么流转？"同上触发"——上一条是什么来着？

同样这行字，业务化的写法：

> **unknown（待认领）→ running（执行中）**
> **触发者**：部署调度器线程（`core/deploy_executor.py:118`）从线程池认领排队任务。
> **业务动作**：执行下发——调度器把任务标记为执行中，占用一个并发槽位（上限 2），
> 开始逐 step 拉起 Ansible 子进程。
> **业务意义**：任务从"已受理"进入"实际占用机器资源"阶段；此刻起任务可以被取消但不能被删除，
> 因为 Ansible 子进程可能已经对目标主机产生了部分变更。

差别不在字数，在于**读者看完知道这台机器在业务世界里干了什么**。

### 1.2 每个状态必须有业务定义

状态业务定义表是状态机章节的**第一张表**，在任何迁移表和状态图之前：

| 状态字面量 | 业务含义 | 谁让它进入 | 离开它意味着什么 |
|---|---|---|---|
| `unknown` | 已受理未开工：记录已落库，但调度器尚未认领 | 用户提交部署请求时（API 层写入） | 意味着任务开始占用并发槽位、真正开始影响目标主机 |
| `partial` | 部分成功：部分主机完成、部分被跳过 | 执行器在主机级异常分支写入 | 意味着需要人工补跑，被跳过的主机仍处于旧版本 |

硬性要求：

1. **每个枚举值一行，一个都不能省**——包括 `unknown` 这类"看起来像解析失败"的状态。
   它恰恰是最需要解释的：它是"记录先于调度存在"的产物，还是迁移兜底，还是废弃残留？
   这三种成因的业务含义完全不同。
2. **解释不了就标 `needs_confirmation=true` 进待确认清单，禁止照抄字面量充数**。
   "unknown（含义待确认）"比"unknown"诚实，比编一个解释安全。
3. 状态的业务含义要回答"**此刻业务世界里什么是真的**"（资源已占用 / 款已到账 / 库存已锁定），
   不是复述状态名（"running 就是运行中"）。

### 1.3 迁移表七列（Phase 1 的 `20-state-machines.json` 对齐此结构）

| 列 | 来源 | 反例（不合格） | 正例 |
|---|---|---|---|
| 当前状态 | 枚举 + 赋值点回溯 | `unknown` | 待认领（unknown） |
| 事件 / 触发者 | `callers` 回溯调用链 | —（不写） | 调度器线程认领（`deploy_executor.py:118`） |
| **业务动作** | 赋值点上下文 | —（缺失） | 执行下发：占用并发槽位、拉起 Ansible |
| 目标状态 | 赋值语句 | `running` | 执行中（running） |
| 副作用 | 赋值后代码路径 | —（缺失） | WebSocket 推送状态变更；task 开始计时 |
| **业务意义** | 综合推断（推不出标待确认） | —（缺失） | 任务从受理进入实际影响主机的阶段，可取消不可删 |
| 代码位置 | 赋值点 file:line | —（缺失） | `core/deploy_executor.py:118` |

其中**业务动作**和**业务意义**两列是 R12 新增的硬要求，schema 里对应
`transitions[].biz_action` / `transitions[].biz_meaning` / `transitions[].actor`，
states 对应 `states[].biz_definition`。

**业务动作参考词表**（写 biz_action 时从中选或用同层级动词，禁止留空）：
任务创建 / 资源占用 / 资源释放 / 执行下发 / 执行中断 / 完成回执 / 失败登记 /
补偿回退 / 人工介入 / 审核通过 / 审核驳回 / 锁定 / 解锁 / 扣减 / 回补 / 通知触发。

### 1.4 HTML 标记约定（R9-7 检查的就是这些）

```html
<section data-sm="部署任务状态机">
  <!-- 状态业务定义表：每个状态一行，≥20 可见字符 -->
  <tr data-sm-state="unknown">
    <td>unknown</td>
    <td>已受理未开工：记录已落库但调度器尚未认领，业务上是"排队等槽位"。</td>
  </tr>
  <!-- 迁移业务含义表：每条迁移一行，≥40 可见字符且必须含业务动词 -->
  <tr data-sm-tx="unknown->running">
    <td>unknown → running</td>
    <td class="sm-biz">触发者：调度器线程认领（core/deploy_executor.py:118）。
      业务动作：执行下发——占用并发槽位、逐 step 拉起 Ansible。
      业务意义：任务开始实际影响目标主机，可取消不可删除。</td>
  </tr>
</section>
```

## 2. R13 · 流程四层拆解

**规则表述**：面对多主流程、主流程内嵌套子流程的系统（微服务尤甚），
流程必须按 **系统级 → 主流程 → 子流程 → 关键方法** 四层拆解，
每层显式标注层级归属、调用链（file:line）、分支条件；
每个子流程必须用一句话说清"它在整体业务里负责什么"。
落地标记由 `check-content-depth.mjs`（R9-8）机器检查。

### 2.1 四层各写什么

| 层级 | 标记 | 写什么 | 篇幅感 |
|---|---|---|---|
| **系统级** | `data-level="system"` | 系统在更大业务链路里的位置（上下游、它吃进什么吐出什么），一张系统上下文图 | 一节 |
| **主流程** | `data-flow="X"` + `data-level="main"` | 一条端到端业务主线（如"入库全流程"），内部五个维度按 R5 写 | 一章 |
| **子流程** | `data-level="sub"` | 主流程内一个可独立命名的业务环节（如"上架"），必须有**职责一句话** + 调用链 + 分支条件 | 一小节 |
| **关键方法** | `data-level="method"` | 子流程里的核心函数：入参出参、判断逻辑、为什么值得单独讲 | 段落内 |

### 2.2 硬性要求

1. **每个 `data-level="main"` 的流程至少要有 1 个 `data-level="sub"` 子流程**。
   "主流程"只有一段概述没有任何子环节拆解，等于只有目录没有内容。
2. **子流程必须带调用链**：从入口方法到该子流程的调用路径（`a.py:f → b.py:g → c.py:h`），
   由 codegraph `callers`/`callees` 提供事实底座，不许凭目录结构猜。
3. **分支条件写在发生分支的那一层**：子流程内部判断（如"波次冻结失败走人工处理"）
   不要上提到主流程层写，否则读者不知道条件是哪一段代码做的判断。
4. **子流程职责一句话**必须回答"**抽掉它，整体业务断在哪**"（如"没有上架环节，
   收货后的库存永远处于待上架不可用状态，拣货员永远看不到货"）。

### 2.3 微服务嵌套场景

一个主流程跨多个服务时，子流程按"**服务边界**"归组：每个子流程标注它落在哪个服务/仓库，
跨服务调用点单独标注（HTTP/MQ/共享表），跨域补偿路径按 `references/01` 跨域场景的要求补全。
调用链在服务边界处显式断开标注（`order-svc:create → HTTP POST → wms-svc:receive`），
不要把两个服务的调用链连成一条看起来连续的线。

### 2.4 标记约定（R9-8 检查的就是这些）

```html
<section class="flow" data-flow="入库全流程" data-level="main">
  <div data-r5="main">…（R5 五维度照旧）…</div>

  <div class="subflow" data-level="sub" data-subflow="上架">
    <h4>子流程：上架（putaway）—— 职责：把收货暂存区的货落到具体储位，
      抽掉它收货库存永远不可用、拣货永远看不到货</h4>
    <p>调用链：<code>api/receipt.py:confirm_receipt → wms/putaway.py:gen_task →
      wms/putaway.py:pick_location</code>。分支条件：<code>pick_location</code>
      按储位混放策略分支——空储位直接落、混放储位校验 SKU 一致、
      危险品走专属区（wms/location_policy.py:31）。</p>
    <p>关键方法 <code data-level="method">pick_location</code>：
      输入 SKU 与数量，输出目标储位；核心逻辑是按"拣货动线距离最近"排序候选储位，
      这是仓库拣货效率的直接决定因素。</p>
  </div>
</section>
```

## 3. 企业级业务解读：让"外行"读懂单据与库存

R3（业务 70/30）解决的是比例，这一节解决的是**具体写法**——尤其面向 WMS/ERP/MES 这类
"术语密度极高"的企业系统。目标读者是**没做过仓储的新人**，不是同行。

### 3.1 业务背景概述怎么写（对应 wiki 第 01 章）

四件事按顺序写，缺一件就是背景没交代完：

1. **这个系统解决什么问题**：不写"本系统是一个 WMS"，写"仓库每天收发几万件货，
   靠纸质单据和老师傅记忆会出现账实不符、找货靠人、错发漏发——本系统把'每一件货
   在哪个储位、归哪张单据管'变成数据库里可查的事实"。
2. **服务谁**：仓库经理、仓管员、拣货员、财务各拿它做什么。
3. **业务体量**：日单量、SKU 数、库位规模的量级（从配置/数据/注释里找线索，找不到标待确认）。
4. **两条线**：单据流（订单→波次→拣货任务→出库单）与实物流（货从收货区→暂存区→储位→
   拣货区→发运区）是同一件事的两种记录方式，后续所有章节按这两条线交叉讲。

### 3.2 术语通俗化四段式（R4 三段式的扩展，企业系统必用）

R4 的三段式（字面定义/白话/业务场景）对通用系统够用，对企业系统加第四段
**代码对应位置**——没有第四段，术语表就还是词典，读者对不上号：

```json
{
  "term": "波次（wave）",
  "plain": "把几十上百张订单按承运商截单时间/拣货动线合并成一『锅』一起拣，",
  "why":   "否则拣货员一张订单跑一趟仓库，一天走不出几单",
  "position": "波次是『拣货任务』的打包单位，处在订单和拣货任务之间",
  "code": "wms/wave.py:release_wave；波次状态字段 shipment_batches.status"
}
```

WMS 高频术语的白话基准（写词汇表时的对照，禁止只写"波次就是 wave 的翻译"）：

| 术语 | 白话 |
|---|---|
| 入库 / 出库 | 货进仓库 / 出仓库这两个方向的全部动作的统称，各自由一组单据驱动 |
| 上架 | 收货后把货从暂存区落到具体储位——落位之前这些货拣货员看不见 |
| 拣货 | 按任务单把货从储位取下来；拣货任务的路径顺序直接决定仓库效率 |
| 波次 | 把一批订单合并成一锅拣，按承运商截单时间或拣货动线分组 |
| 盘点 | 数一遍实际库存跟账面对不对得上；差异要生成调整单走审批 |
| 库存锁定 | 这部分数量已被某张单据"预订"，别人不能再动它——超卖事故的防线 |

**每个术语必须能在代码里指出对应位置**（类/表/枚举/关键函数），指不出来说明
这个术语是外部知识，进待确认清单让业务方补。

### 3.3 单据流转与库存流转对照表（数据模型章的核心交付）

企业系统的"数据模型"不能只画 ER 图。WMS 类系统必须交付一张
**单据-库存双线对照表**：每行 = 一种单据，列出它驱动什么实物动作、改变哪些库存字段
（可用量/锁定量/在途量）、它自己的状态机怎么走。ER 图回答"表长什么样"，
这张表回答"货和账怎么动"——后者才是新人真正缺的东西。

## 4. wiki 级统一输出结构（v2）

用户要求文档"跟项目详细 wiki 一样"。只交 5 章（背景/术语/流程分层/入口调用链/结论待确认）
撑不起 wiki——缺的是**让它能被当工具书查**的那些章节。最终 14 章结构及各章的规则落点
见 `references/06-output-structure-and-map.md`（已升级）。
用户原有 5 项之外补齐的：文档信息与证据等级、整体架构（R6）、系统边界与外部依赖、
数据模型与单据流转、规则手册、配置与开关、FAQ/排障、附录（枚举/状态机总表/变更热点）。
其中**第 12 章待确认清单之前应有一节"结论"**：用 5-10 句话给管理层级别的摘要
（这个系统是什么/健康度/最大的三个风险），这是 wiki 的"首页摘要"，新人和管理员都先读它。

`check-content-depth.mjs`（R9-9）会核对核心章节是否缺席（warn 级），
小型项目可有意识省略部分章节，但要在文档信息页写明省略原因。
