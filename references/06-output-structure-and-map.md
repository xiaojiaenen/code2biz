# 输出结构：业务地图与学习路径

避免"新人不知道从哪学起"，最终交付物不是把各阶段产出简单拼接，而是按下面的递进结构组织，并显式给出阅读顺序建议。

## 文档目录结构（单文件 HTML 的左侧导航，v2 · wiki 级）

**这版结构是被"统一输出结构够不够 wiki"这个问题推出来的**。原有 8 章对"讲明白业务"够用，
对"当工具书反复查"不够用——wiki 的特征是：新人能从头读到尾，老手能直接跳到某一章查证据。
v2 按这个标准补了 6 章：

```
00 文档信息与业务地图   代码版本（commit）/分析日期/证据等级图例（✅代码确证 ⚠️推断 ❓待确认）
                        /核心主线 vs 支撑模块 vs 边缘功能/按角色的推荐阅读路径/新人自查清单
01 业务背景概述         解决什么业务问题、服务谁、业务体量、单据流与实物流两条线（R12/R13 前置）
02 核心概念与术语表     术语四段式（字面/白话/单据-实物流位置/代码位置，R4 企业系统扩展版）+ 跨域叫法
03 整体架构             架构拆解五问（R6）+ 顶层 archify 图 + 图下方业务解读
04 系统边界与外部依赖   上下游系统、第三方服务、消息契约、跨域补偿路径（跨域场景的落点）
05 数据模型与单据流转   实体关系 + 单据-库存双线对照表 + 各单据状态机（R12 业务化交付）
06 流程分层清单         R13 四层拆解（系统→主→子→方法）内嵌 R5 五维度 + 状态流转业务含义（R12）
07 关键代码入口与调用链 入口点清单（file:line）+ 每条主流程的调用链索引（R13 的方法层汇总）
08 规则手册             业务规则 + 原始数值边界 + 交互式规则计算器（R2 源码可追溯）
09 配置项与开关         feature flag / 阈值配置 / 环境差异清单，每项写"改变它业务上会怎样"
10 角色与权限           角色-权限矩阵 + 每条流程权限约束的汇总（R5 permission 维度的查表形态）
11 入口点覆盖率         check-entry-coverage.mjs 报告（R8），可点名"还有哪几条没处理"
12 结论与待确认清单     先 5-10 句结论摘要（系统是什么/健康度/最大三个风险），再 flagged+待确认清单
13 FAQ 与排障指南       新人常见问题 + 常见故障的业务表现与排查入口（从异常流程反推）
14 附录                 枚举值映射总表、状态机总表、变更热点（git 活跃度）、全文术语索引
```

**相对用户最初提出的 5 章骨架（背景/术语/流程分层/入口调用链/结论待确认）补齐的部分**：
文档信息与证据等级（没有它，三个月后没人知道这份文档对应哪版代码）、整体架构、
系统边界与外部依赖（跨域链路的落点，单看代码最容易漏）、数据模型与单据流转
（企业系统的核心章节，光有 ER 图不够）、规则手册、配置与开关、角色与权限、
FAQ 与排障、附录。小型项目可有意识省略其中部分章节，但要在第 00 章写明省略原因——
`check-content-depth.mjs` 的 R9-9 会以 warn 级点名缺失的核心章节。

## v1 → v2 的差异（为什么改）

- 第 00 章是新增的：wiki 的第一页永远是"这份文档是谁、基于哪版代码、什么时候写的"。
  证据等级图例让"代码确证"和"推断"在视觉上可区分，继承"绝不编造"的原则。
- 业务背景概述从"架构章节的一小节"独立成第 01 章：R13 要求系统级视角（上下游、两条线），
  它是流程分层的入口，不配架构图配故事。
- 系统边界（04）独立：跨域补偿路径是实测中最容易被漏的部分，值得一个专属章节。
- 数据模型与单据流转（05）：企业级系统（WMS/ERP）单靠 02 领域模型讲不清"货和账怎么动"，
  单据-库存双线对照表 + 状态机业务化（R12）落在这里。
- FAQ（13）和附录（14）是 wiki 和报告的分界线：报告读完就归档，wiki 会被反复查。

**对比 v1 的差异（历史）**：
- 把"整体架构"独立成第 01 章（之前是按 Phase 3 出图但没强约束文字解读），R6 五问 + 配套业务解读是新增硬要求 → v2 中对应第 03 章
- 把"入口点覆盖率"独立成章（之前要求"放进单文件 HTML 独立一节"但没位置），R8 的可点名清单 → v2 中对应第 11 章
- "待确认清单"独立成章（之前在文末"待确认"），更显眼 → v2 中对应第 12 章，且前置"结论"摘要
- 词汇表升级为术语三段式（R4）→ v2 中升级为四段式（企业系统加代码对应位置）

## "业务地图"怎么判定核心 vs 边缘（落在第 00 章）

不要凭空猜测重要性，用可观测信号辅助判断，但最终请用户校准（这一步几乎必须有人工确认，代码分析给的是候选排序，不是最终结论）：

- 模块被其他模块依赖的次数（被引用越多，通常越核心；用 codegraph `callers` 统计）
- 涉及的数据表在整个数据库里的关联度（外键指向/被指向数量）
- 代码变更频率（如果有 git log 可用：越常被修改，可能是越活跃的核心业务，但也可能是不稳定的边缘功能——两种可能都要跟用户确认哪个成立）
- 用户在任务开始时如果已经指出了"核心主线是什么"，以用户说法为准，不允许用代码信号覆盖

生成候选排序后，用一句话呈现依据（"该模块被 12 个其他模块引用，判定为核心"），让用户能快速确认或纠正，而不是直接把排序当作确定结论写死。

## 学习路径的"合格标准"（落在第 00 章末尾）

在第 00 章业务地图末尾给出一个简短的自查清单，帮助新人判断自己学到什么程度算合格，例如：

- 能否独立画出某条核心链路的**正常路径 + 至少两条异常路径**（R5 异常流程落点）
- 能否说出某个核心字段的 3 个可能取值分别代表什么业务状态（R4 枚举映射落点）
- 遇到词汇表里的黑话是否已经不需要查表（R4 三段式落点）
- 能否指出整体架构当前最吃力的点 + 未来最可能成为瓶颈的点（R6 架构优劣势落点）

这个清单应该基于实际生成的文档内容定制，不允许用通用模板。
