# 内容深度门禁（R9 / R10 / R11 + R12/R13 的检查落点）

> 这份参考解决一个被 Russh 实测暴露的事故：**规则写得极细，但没有一个脚本检查它，于是规则不是约束，只是愿望。**
> 配套脚本：`scripts/check-content-depth.mjs`。可运行的通过样例：`examples/content-depth-pass-sample.html`。
> R12（状态流转业务化）/ R13（流程四层拆解）的规则本体在 `references/13-business-deep-reading.md`，本文件收录它们的检查约定。

## 0. 先看数据：为什么需要这一层

Russh 项目实测产物（`test-instance/russh-business-docs.html`，356 KB）在加上本门禁之前的真实状态：

| 指标 | 实测值 | 规则要求 | 结论 |
|---|---|---|---|
| 正文可见字符（中文） | 9508（中文 2593） | — | 90%+ 体积是 7 张 SVG |
| 7 张图的图注长度 | 20 ~ 70 字符 | 每张 200-400 字 | 全部不达标 |
| 架构章节正文 | ~874 字符 | R6 五问全覆盖 | 只答了拓扑一问 |
| `失败后果` / `降级` / `幂等` / `并发冲突` | 各 0 次 | R5 强制写后果 | 异常维度整体缺失 |
| `设计目的` / `为什么` / `瓶颈` / `单点` | 各 0 次 | R6 强制答动机与问题 | 架构章节无动机无判断 |
| recorded 占已处理入口点 | **76.3%**（29/38） | — | 四分之三的业务一句话带过 |
| "同上触发，未单列" | **15 处** | 禁止占位 | 生成器没解析出触发条件就直接占位 |
| `&amp;quot;` 双重转义 | **10 处** | — | 浏览器正文直接显示 `&quot;` 字样 |

**最关键的一行不在表里**：这份产物**通过了当时 `check-final-html.mjs` 的全部检查**。

这说明两件事：

1. `check-final-html.mjs` 管的是"能不能打开"，它尽职了，但它的职责边界就到那儿为止。
2. R5 / R6 / R7 在 `references/02` 和 `references/11` 里白纸黑字写着"必须全部答出，不能跳过"，**但没有任何脚本检查这句话**，于是实测产物照样跳过，且无人拦截。

**结论：一条规则如果没有对应的可执行检查，它的实际效力等于零。** R9/R10/R11 就是把 R5/R6/R7 从"要求"变成"门槛"的那一层。

## 1. R9 · 内容深度可验证

**规则表述**：R5（流程五维度）、R6（架构五问）、R7（图注业务解读）、R8（小业务展开）的每一项落地，都必须在最终 HTML 里留下**机器可定位的标记**，并能通过 `check-content-depth.mjs`。不写标记 = 无法验证 = 视为未交付。

### 1.1 标记约定总表

这些 `data-*` 属性是纯标记，**不改变视觉呈现**（不需要配套 CSS，加了也不影响 archify 的设计 token）。它们的唯一作用是让"讲清楚了没有"这件事变得可判定。

| 标记 | 放在哪 | 内容下限（可见字符） | 对应检查 |
|---|---|---|---|
| `<figure class="arch-figure" data-fig="名字">` | 每张内联图外层 | — | R9-1 |
| `<figcaption class="arch-caption">` | figure 内部，SVG 之后 | **200** | R9-1 |
| `data-r6="<key>"` | 架构章节的五个小节容器 | topology 120 / purpose 120 / responsibility 200 / dependency 120 / assessment 150 | R9-2 |
| `data-flow="<流程名>"` | 每条核心流程的容器 | — | R9-3 |
| `data-r5="<key>"` | data-flow 内部的五个维度块 | main 200 / branch 60 / exception 150 / data 100 / permission 60 | R9-3 |
| `data-entry-id="<id>"` + `data-entry-status="recorded"` | 入口点表里的每一行 | recorded 行 **60** | R9-4 |
| `class="entry-business"` | recorded 行的业务说明单元格 | **60** | R9-4 |
| `data-rule="<规则名>"` | 规则手册里每条规则的容器 | 需含源码位置 | R9-6 |
| `data-sm="<状态机名>"` | 每台状态机的章节容器 | 状态定义 + 迁移含义 | R9-7 |
| `data-sm-state="<状态字面量>"` | 状态业务定义表的每一行 | **20** | R9-7 |
| `data-sm-tx="<from->to>"` | 迁移业务含义表的每一行（含 `class="sm-biz"` 单元格） | **40** + 业务动词 + 源码位置 | R9-7 |
| `data-level="system\|main\|sub\|method"` | 流程分层标记（R13 四层） | sub 需 ≥30 字符职责 | R9-8 |
| `data-subflow="<子流程名>"` | 子流程容器，与 data-level="sub" 同用 | 需含调用链（file:line） | R9-8 |

`data-r6` 的五个 key：`topology` / `purpose` / `responsibility` / `dependency` / `assessment`。
`data-r5` 的五个 key：`main` / `branch` / `exception` / `data` / `permission`。

**完整可复制的骨架见 `examples/content-depth-pass-sample.html`**（这个文件本身就是门禁的通过样例，改之前先照着它的结构写）。

### 1.2 图注：图不是解读，图注才是

每张图下方的 `figcaption` 必须写 **200-400 可见字符**，内容按这个顺序：

1. **这张图在回答什么问题**（一句话）
2. **每个域/模块各自的业务定位**（不是"用户服务负责用户"，是"它承载账号体系、登录态、组织树、权限组四项能力"）
3. **一条值得注意的连线或节点**（为什么值得注意：它是唯一的异步调用、它是单点、它有隐性约束）
4. **读这张图容易误判的地方**（箭头是调用方向不是数据方向、虚线是待确认、灰色节点是外部系统）

**反面案例（实测产物里的真实图注，46 字符）**：

> 部署主链路 + 授权校验链路（其余业务 API 见数据层说明）。

这句话同时犯了两个错：**图注不够长**，**还把 29 条业务 API 一句话归堆掉了**。R10 会单独拦第二种。

### 1.3 异常维度：必须有"后果"这一侧

R5 的 `exception` 块除了字数要求，还会检查**两侧关键词同时存在**：

- **触发条件侧**：触发 / 条件 / 当 / 如果 / 失败 / 超时 / 异常 / 冲突 / 不足 / 中断 / 越权
- **业务后果侧**：后果 / 回退 / 回滚 / 降级 / 通知 / 重试 / 补偿 / 告警 / 终态 / 变为 / 标记为 / 拦截 / 拒绝

只有一侧的，脚本会报错。这不是关键词游戏——"如果失败则报错"这句话里既有"如果"也有"失败"，但读者看完仍然不知道**失败之后数据变成什么样、用户看到什么、要不要人工介入**。写异常的最小单元是三段式：

```
触发条件 → 兜底逻辑 → 业务后果
```

正例：

> **单步超时**：触发条件是单步执行超过 3600 秒，兜底逻辑是杀掉 Ansible 子进程并把该步标记为 failed，
> 业务后果是任务立即终止、已完成的步骤保持成功不回滚，需要人工从失败步续跑。

### 1.4 架构五问：purpose 和 assessment 是最容易糊弄的两问

- `purpose` 必须真的在回答"为什么"——脚本检查是否出现：为什么 / 目的 / 为了 / 因为 / 诉求 / 当初 / 背景。只写"本系统采用分层架构"会被拦下。
- `assessment` 必须真的在说问题——脚本检查是否出现：问题 / 瓶颈 / 风险 / 优势 / 适配 / 吃力 / 隐患 / 不足 / 局限。只夸架构优势不写现存问题的，等于没答。

`responsibility` 的下限最高（200 字符），因为"各模块职责"是最容易被写成"用户服务负责用户"这种废话的地方。

### 1.5 章节级"图代文"检测

单个图注达标还不够——脚本还会按 `<section>` 切分，检查**每个含图章节的正文总量 ≥ 图数 × 200**。

这条是专门针对"每张图都配了 250 字图注，但整章除了图注一个字没有"这种情况。图占了体积，不能让它同时占掉内容。

## 2. R10 · 占位符零容忍

**规则表述**：最终交付物里不允许出现任何占位文本。占位不是"简要带过"，是**这条业务压根没讲**——而且比不写更有害，因为它让读者以为文档已经覆盖了。

### 2.1 黑名单（`check-content-depth.mjs` 直接命中即 error）

| 占位模式 | 典型形态 | 为什么必须拦 |
|---|---|---|
| `同上…未单列` | "（同上触发，未单列）" | 生成器没解析出触发条件就填了占位。实测产物里 15 处，等于 15 条状态迁移的触发条件全是空的 |
| `见…说明` | "其余业务 API 见数据层说明" | 归堆。实测里这一句话把 29 条 API 全部带过 |
| `待补` / `待补充` | "（待补）" | 明确承认没写，就不该出现在交付物正文里（应该进第 06 章待确认清单） |
| `TODO` / `TBD` / `FIXME` | — | 开发标记，不属于文档 |
| `如上图所示` / `如下图所示` | — | 伪引用，没给出任何信息 |
| `具体可参考源码` / `详见文档` | — | 伪引用。给行号算写了，不给行号不算 |
| `略见上文` / `略述下述` | — | 归堆 |
| `其余…同理/类似/同上` | "其余接口逻辑类似" | 等于没写 |

### 2.2 三个常见借口的反驳

**"小业务不值得展开，一句话带过效率更高。"**
Russh 实测里被一句话带过的 29 条，恰恰包含了定时任务、WebSocket、消息消费这些非 HTTP 入口——它们在代码里存在，在文档里失踪。真正漏业务的地方从来不是主流程，是这些"看起来不重要"的角落。所以展开的下限只要求 60 字符（见 §3），这不是高要求。

**"信息不足，没法写。"**
那就写"信息不足"这个事实本身，标 `flagged` 进第 06 章待确认清单。**不要让占位符留在正文里假装已覆盖**——这是 R10 唯一的要求。

**"位置不够，展开会太长。"**
R9 要求的是"精简但完整"，不是"详细"。recorded 条目 60 字符的要求，对应的是一句话说清"谁在什么场景下用它、拿什么换什么、失败了会怎样"，不是写一段论文。

## 3. recorded 的正确用法：小业务怎么讲清楚

R8 的三态里，`recorded` 原本的定义是"业务逻辑单薄，给一行归类说明即可"。**这个定义被实测证明是有害的**——它成了 76% 的入口点逃避展开的合法出口。

### 3.1 重新定义

| 状态 | 新定义 | 交付要求 |
|---|---|---|
| `detailed` | 走完 Phase 1-2 全套提取的完整流程 | 五维度（R5）全写 |
| **`recorded`** | **业务动作单一（典型是 CRUD / 单表查询），但仍然是真实业务** | **必须展开成"输入 / 输出 / 业务目的 / 失败边界"四要素，≥60 可见字符，且带在文档里出现** |
| `flagged` | 存在但存疑（模板/脚手架/疑似废弃/动机不明） | 进第 06 章待确认清单，说明存疑理由 |

**判断标准变了**：不是"这个业务重不重要"，而是"这个动作是不是单一的"。重要的业务必须 `detailed`，单一的动作才允许 `recorded`，但 `recorded` **不等于一句话**。

### 3.2 recorded 四要素模板

```
<业务目的>：<谁>在<什么场景>下用它，用来<达成什么>。
输入：<关键入参>，输出：<返回什么>。
失败边界：<最容易踩的坑 / 失败时是什么表现 / 有没有静默失败>。
```

正例（68 字符，来自通过样例）：

> 运维在部署前查看主机台账，用来确认目标主机在线、组件安装状态是否正常。
> 输入是可选的分页参数，输出是主机列表含 IP、在线状态、组件清单。业务目的只有一个：
> 给部署动作提供目标选择的依据。失败边界是数据库不可用时返回空列表而非报错，
> 前端会误判为"没有主机"。

对比实测产物里那句"其余业务 API 见数据层说明"——差别不在长短，在于**前者能让读者真的知道这个接口是干嘛的**。

### 3.3 recorded 占比上限 50%

如果 `recorded / 已处理入口点 > 50%`，`check-content-depth.mjs` 直接判不合格。

**这不是拍脑袋的阈值。** 它的含义是：如果你发现一半以上的业务都"动作单一、不值得展开"，那么大概率不是业务真的都这么简单，而是**你的入口点分类粒度太粗**——把几个本该 `detailed` 的流程合并成了 `recorded`，或者根本没看进去就标了 `recorded`。真遇到 CRUD 密集型的管理后台，正确的做法是**按资源分组**展开（"节点管理这一组接口共同完成主机台账维护，其中 DELETE 是软删…"），而不是逐条标 recorded 然后一句话带过。

## 4. R11 · 实体转义正确

最终 HTML 正文里不允许出现 `&amp;quot;` 这类双重转义——浏览器会直接把 `&quot;` 五个字符显示给读者看。

典型成因：对**已经转义过一次**的文本又转义了一遍（常见于"先把片段塞进属性值、再整个塞进 srcdoc/模板字符串"这类链路）。R1 禁掉 iframe srcdoc 之后这条链路已经不存在，但转义代码本身可能还留在生成器里。

`check-final-html.mjs` 和 `check-content-depth.mjs` **两边都查这一项**：前者是从"渲染正确性"兜底，后者是从"内容可读性"检查。交付前两个脚本都要跑。

## 5. 怎么用这两个脚本

### 5.1 什么时候跑

```
Phase 2 结束（文档内容写完，还没打包）  → 跑 check-content-depth.mjs（此时最容易改，改的是内容不是 HTML）
Phase 5 结束（打包成单文件之后）        → 两个都跑，作为交付前硬性门禁
```

**强烈建议在 Phase 2 就跑一次**，而不是等到 Phase 5 打包完。打包之后报"图注不足 200 字"，改的是内容；Phase 2 报同样的问题，改的是段落。后者的修改成本低一个数量级。

### 5.2 命令

```bash
# 内容深度门禁（推荐带 coverage 和 entries，能多查两项）
node scripts/check-content-depth.mjs <final.html> \
  --coverage <coverage-report.json> \
  --entries <entry-points.json> \
  --report content-depth-report.json

# 交付前用 --strict：warning 也算不合格
node scripts/check-content-depth.mjs <final.html> --strict

# 单文件完整性门禁（R1 / 离线 / 转义）
node scripts/check-final-html.mjs <final.html>
```

`--report` 产出的 JSON 报告建议直接作为第 07 章"入口点覆盖率"的相邻一节交付给用户——让用户能看到"这份文档的内容深度是被机器核过的，具体哪几项通过了"。

### 5.3 报错 → 怎么修（对照表）

| 报错信息 | 根因 | 怎么改 |
|---|---|---|
| 图「X」的图注只有 N 可见字符 | 图注写成了标题或一句话 | 按 §1.2 的四段结构补到 200-400 字符 |
| 章节「X」有 N 张图，正文只有 M 字符 | 图代文 | 给这一章补模块职责/数据流/边界说明，不是给图注注水 |
| R6 缺「purpose」一问 | 架构章节没分五问写 | 按 §1.4 补小节，加 `data-r6="purpose"` |
| R6「purpose」没出现"为什么" | 只写了"是什么" | 补业务体量 / 迭代节奏 / 团队规模 / 当初的约束 |
| R6「assessment」没出现"瓶颈" | 只夸不批评 | 补现存问题 + 业务扩张到什么量级会扛不住 |
| 流程「X」缺 R5 维度「exception」 | 漏写异常 | 按 §1.3 三段式补，触发条件和后果两侧都要有 |
| 异常维度没写业务后果 | 只写了"失败则报错" | 补数据回退到哪、用户看到什么、要不要人工介入 |
| N 条 recorded 业务说明不足 60 字符 | 一句话带过 | 按 §3.2 四要素模板补 |
| recorded 占比 X% 超过 50% | 分类粒度太粗 | 把成组的按资源分组展开，或把确实复杂的改成 detailed |
| 清单里有 N 条 recorded 在文档里找不到 | 文档里根本没这一节 | 补第 07 章入口点清单，每条都带 `data-entry-id` |
| 占位文本【未单列】出现 N 次 | 生成器没解析出触发条件 | 回代码里查这 N 条的真实触发条件；查不到就标 flagged 进第 06 章 |
| 没有任何 data-sm，正文有 N 处裸字面量流转 | 状态机整章只有 `unknown → running` 式罗列 | 按 references/13 §1 补状态业务定义表与迁移七列表，每条迁移带 data-sm-tx |
| 状态机「X」的状态「Y」业务定义只有 N 字符 | 复述状态名凑数 | 按"谁让它进入/此刻业务世界里什么是真的/离开意味着什么"三问重写；解释不了标待确认，禁止照抄字面量 |
| 状态机「X」的迁移「Y」没有业务动词 | 只写了状态字面量和事件名 | 补 biz_action（任务创建/资源占用/执行下发/完成回执…词表见 references/13 §1.3）与 biz_meaning |
| 流程「X」标注 main 层却没有 sub 子流程 | 只有主流程概述没有环节拆解 | 按 references/13 §2.1 把主流程切分成可独立命名的业务环节，每个加 data-level="sub" |
| 子流程「X」没有调用链 | 凭目录结构猜的流程 | 用 codegraph callers/callees 取真实调用路径写进 data-subflow 内容 |
| 发现 N 处双重转义 | 转义链路重复转义 | 找到生成器里 escape 了两次的那一行；R1 已禁 srcdoc，该链路多半是历史残留 |
| 没有任何 data-r6 / data-r5 标记 | 没按约定写 | 照 `examples/content-depth-pass-sample.html` 补结构 |

### 5.4 别为了过门禁而注水

这套检查是**关键词 + 字数 + 结构**的机械组合，它能拦住"没写"，拦不住"写了但没用"。以下行为虽然能让脚本变绿，但违反了这套 skill 的根本原则（见 SKILL.md 开头：不编造、不粉饰）：

- 在图注里重复图的标题凑字数
- 在 `assessment` 里写"目前没有明显瓶颈"来命中"瓶颈"这个词（**这条尤其要避免**——如果确实没发现瓶颈，就写"未发现明显瓶颈，因为 X、Y、Z 三处的容量在业务量级下都不构成约束"，把判断依据写出来）
