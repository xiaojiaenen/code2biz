# 输出结构：业务地图与学习路径

避免"新人不知道从哪学起"，最终交付物不是把各阶段产出简单拼接，而是按下面的递进结构组织，并显式给出阅读顺序建议。


## "业务地图"怎么判定核心 vs 边缘

不要凭空猜测重要性，用可观测信号辅助判断，但最终请用户校准（这一步几乎必须有人工确认，代码分析给的是候选排序，不是最终结论）：

- 模块被其他模块依赖的次数（被引用越多，通常越核心；用 codegraph `callers` 统计）
- 涉及的数据表在整个数据库里的关联度（外键指向/被指向数量）
- 代码变更频率（如果有 git log 可用：越常被修改，可能是越活跃的核心业务，但也可能是不稳定的边缘功能——两种可能都要跟用户确认哪个成立）
- 用户在任务开始时如果已经指出了"核心主线是什么"，以用户说法为准，不允许用代码信号覆盖

生成候选排序后，用一句话呈现依据（"该模块被 12 个其他模块引用，判定为核心"），让用户能快速确认或纠正，而不是直接把排序当作确定结论写死。

## 学习路径的"合格标准"

在 00 业务地图末尾给出一个简短的自查清单，帮助新人判断自己学到什么程度算合格，例如：

- 能否独立画出某条核心链路的**正常路径 + 至少两条异常路径**（R5 异常流程落点）
- 能否说出某个核心字段的 3 个可能取值分别代表什么业务状态（R4 枚举映射落点）
- 遇到词汇表里的黑话是否已经不需要查表（R4 三段式落点）
- 能否指出整体架构当前最吃力的点 + 未来最可能成为瓶颈的点（R6 架构优劣势落点）

这个清单应该基于实际生成的文档内容定制，不允许用通用模板。
