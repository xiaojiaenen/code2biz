00 业务背景概述

Russh 解决的问题是：Ansible 手工运维动作散在各个老师傅的终端历史里，同一套 playbook 谁执行、什么时候执行、执行到哪一步全靠口头同步，出问题无法回溯。本系统把"对哪批主机、 跑哪个 playbook、每一步成败"变成数据库里可查、可重试、可审计的任务记录。 服务对象是运维团队（发起与补跑部署）和管理层（看授权用量与部署成功率）。 业务体量是千级任务/天、十级集群（来自配置与注释线索）。它处在运维工具链的执行层： 上游是变更审批（不在本仓库，系统边界章节交代），下游是被纳管的集群主机。

02 核心概念与术语表

任务（deploy task）

白话：一次"对这批机器跑这套脚本"的完整尝试，是运维工作的基本单位—— 不是执行一个命令，而是带着目标、步骤和状态的一条业务记录。 位置：处在"变更审批通过之后、步骤执行之前"，一个任务拆 N 个步骤。 代码对应：表 deploy_tasks，状态字段 deploy_tasks.status，创建入口 api/deploy.py:execute_deploy。

01 整体架构

1.1 架构拓扑

Russh 是一个单体 FastAPI 应用，按职责纵向切分为三层：表现层是 6 个 API 子模块 （nodes / deploy / license / monitor / auth / system），全部挂在同一个 FastAPI 实例上； 业务层是 5 个核心服务模块，其中 deploy_executor 是唯一带异步执行能力的模块； 数据层是 SQLAlchemy + MySQL，外加 Ansible Runner 这个外部进程。 不是微服务，模块之间靠 Python 函数直接调用，没有 RPC 也没有服务注册中心。

1.2 设计目的（为什么这么设计）

选单体 FastAPI 是 2022 年初版上线时的团队规模决定的：当时只有 1 个后端加 1 个前端， 目标是把 Ansible 手工运维动作收敛成可复用的界面操作，业务体量在千级任务/天， 单体加后台线程池足够应对。真正的架构性改动发生在 2023 年：因为商业化需要按节点数授权， 才补了一整套 license_manager 校验中间件横切所有写接口。为什么没有拆服务？ 从代码里能找到的线索是部署动作本身是低频重操作（单集群周级变更）， 吞吐诉求远低于运维可靠性诉求，拆服务带来的分布式事务问题不划算。

1.3 各层 / 各模块职责

api/deploy.py 承载部署任务的创建、重试单步、查询状态三类业务能力， 典型调用方是 Web 部署页与自动化运维脚本，它依赖 DB 的 deploy_tasks / deploy_steps 两张表， 业务约束是同一集群同时只能有 1 个运行中的任务。core/deploy_executor.py 承载真正的执行能力：按 step 顺序驱动 Ansible playbook、汇总每步成败、判定任务终态， 依赖 Ansible Runner 外部进程，全局并发上限 2、单步超时 3600 秒。 core/license_manager.py 承载授权额度校验，被所有写接口横切调用， 超过授权节点数时直接拒绝而不是降级。api/nodes.py 承载主机台账与连通性探测， 是部署动作的前置依赖。

1.4 模块依赖关系

同步调用链只有一条主干：api/deploy.py:execute_deploy 调用 core/deploy_executor.py:start_deploy，后者立即返回 task_id 而不阻塞， 前端拿 task_id 轮询 /api/deploy/{id} 查状态、订阅 /api/deploy/{id}/log WebSocket 拿实时日志。共享数据集中在 deploy_tasks 与 deploy_steps 两张表，读写模式是"API 层写任务、执行器写步骤、前端读两边"。 没有 MQ，异步是靠 ThreadPoolExecutor 实现的。

1.5 架构优势、现存问题、业务适配性

优势：部署动作被完整建模成任务加步骤的两级结构，任何一步失败都能精确定位并重试， 运维排障成本远低于直接跑 Ansible。现存问题：第一，任务状态依赖执行器进程更新， Web 服务重启会让运行中的任务卡在 running，这是目前最主要的单点隐患；第二， deploy_steps 表在单任务步骤数超过百级时查询明显变慢，缺少按 task_id 的复合索引； 第三，并发上限写死为 2，没有按集群规模自适应。业务适配性： 如果纳管集群从当前的十级涨到百级，前两个问题会同时放大——并发上限会先成为瓶颈， 然后卡死任务的概率随任务数线性上升，届时需要把执行器拆成独立进程并引入任务心跳。

03 核心流程

部署主链路（R13 层级：主流程）

主流程

1) 运维在部署页选择目标集群与 playbook，前端 POST /api/deploy； 2) api/deploy.py:execute_deploy 校验授权额度与目标主机在线状态， 写 deploy_tasks（status=pending）并生成 N 条 deploy_steps（status=pending），返回 task_id； 3) core/deploy_executor.py:start_deploy 把任务丢进线程池， 立即把 task 置为 running，逐 step 调 Ansible Runner； 4) 每步执行完回写 step 状态并通过 WebSocket 推送日志； 5) 全部 step 成功后把 task 置为 success，任一步失败则 break 后续步骤并置为 failed 或 partial。 前置条件是目标主机全部在线且未超授权；后置条件是 task 落到终态且所有 step 都有明确状态。

分支流程

按主机类型分支：普通节点走完整安装 playbook，已装组件走跳过安装直接配置； 按来源分支：手动部署要求操作人具 admin 角色，定时巡检触发的部署用系统身份并跳过二次确认。 业务意义在于避免重复安装（省时且避免破坏已有数据）与区分人工操作与自动操作（审计要求）。

异常流程

目标主机不在线：触发条件是探测接口连续 3 次无响应， 兜底逻辑是把该主机从目标列表剔除后继续执行其余主机，业务后果是任务终态判为 partial 而非 failed， 前端列出被跳过的主机由运维人工补跑。单步超时：触发条件是单步执行超过 3600 秒， 兜底逻辑是杀掉 Ansible 子进程并把该步标记为 failed，业务后果是任务立即终止， 已完成的步骤保持成功不回滚，需要人工从失败步续跑。授权额度不足： 触发条件是目标节点数超过 license 上限，兜底逻辑是在建任务前直接拒绝， 业务后果是不产生任何任务记录，前端提示扩容授权。三类异常都不触发告警通知， 仅写入任务日志——这是当前的实现缺口。

数据流转

数据产生于前端提交的表单，加工环节是参数校验与 step 拆分，传输全程走 HTTP 加进程内函数调用， 存储在 deploy_tasks（任务级）与 deploy_steps（步骤级）两张表，无分库分表。 更新方有两个：API 层写任务状态，执行器写步骤状态，同一任务的状态更新由线程池串行保证， 没有版本号或乐观锁。删除策略是软删，任务记录保留 90 天后由运维脚本清理。

权限 / 风控

创建部署任务要求操作人具 operator 及以上角色；重试失败步骤额外要求该任务由本人创建或操作人是 admin。 设计目的是防止运维 A 误重试运维 B 正在处理的任务造成重复执行。 鉴权失败的业务后果是接口直接返回 403 且不产生任务记录，不写入审计日志——这一点需要补。

子流程：任务创建与分发 —— 职责：把一次部署意图变成带步骤清单的可调度任务， 抽掉它运维动作就退回到手工跑 playbook，没有状态、没有重试、没有审计

调用链：api/deploy.py:execute_deploy → core/deploy_executor.py:start_deploy → core/deploy_executor.py:enqueue。分支条件：按目标主机组件状态分支—— 全新主机生成 install+config 两步，已装组件只生成 config 一步 （api/deploy.py:64）；按触发来源分支——手动触发要求 operator 角色， 定时巡检用系统身份跳过二次确认。

关键方法 enqueue：入参是任务 ID， 行为是把任务丢进全局线程池（并发上限 2）并立即返回——返回时任务还没开始跑， 只是"已受理"。这就是任务存在 pending 状态的原因：创建和执行在业务上是两个时刻。

05 部署任务状态机（状态业务化交付）

状态业务定义
pending已受理未开工：任务记录已落库、步骤已拆分，但调度器尚未认领——此刻不占用并发槽位，取消无任何代价。
running执行中：已占用并发槽位（上限 2），Ansible 子进程正在对目标主机产生真实变更——此刻可取消但不可删除。
partial部分成功：部分主机完成、部分被跳过——意味着需要人工补跑，被跳过的主机仍停留在旧版本。
success全部完成：所有步骤回执成功——意味着目标集群已与新版本一致，任务只读。
failed失败终止：某步触发硬性失败中断后续——已完成步骤不回滚，从失败步人工续跑。
迁移业务含义
pending → running 触发者：调度器线程从线程池认领（core/deploy_executor.py:118）。 业务动作：执行下发——占用并发槽位、按步骤清单逐台拉起 Ansible 子进程。 业务意义：任务从"排队等槽位"进入"实际影响目标主机"阶段，取消要杀子进程而非删记录。
running → success 触发者：执行器主循环在最后一个步骤回执成功时（core/deploy_executor.py:203）。 业务动作：完成回执——登记全部步骤耗时并把任务置为终态、通过 WebSocket 通知前端刷新。 业务意义：目标集群版本已收敛，该任务从运维工作集移除，只剩审计价值。
running → failed 触发者：任一步骤返回非零退出码且该步骤标记 break-on-fail（core/deploy_executor.py:187）。 业务动作：失败登记——杀掉残留子进程、后续步骤保持 pending、记录失败步序号供续跑。 业务意义：变更未完成，集群处于"部分新版本"混合态，是排障和补跑的输入。

05b 数据模型与单据流转

核心单据只有一张：部署任务单（deploy_tasks + 子表 deploy_steps）。 它的生命周期就是"部署意图 → 执行凭据 → 审计记录"三段：创建时是意图（pending）， 执行时是凭据（running，凭它可以判断哪台机器被动过），终态后是审计记录（保留 90 天）。 与实物流的对应关系：任务单的每个步骤对应目标主机上一次真实的 playbook 执行， step 状态是"这台机器被改到了哪一步"的唯一真相来源。

12 结论与待确认清单

结论摘要

Russh 是一个单体运维执行系统，核心价值是把 Ansible 手工动作变成可审计的任务记录； 当前健康度中等——功能完整但有两个结构性隐患（执行器单点、并发上限写死）， 最大的三个风险：Web 重启导致任务卡 running、百级步骤查询变慢、异常不触发告警。

待确认清单

  • ❓ partial 终态是否需要自动补跑策略，代码中未见定时重试逻辑，疑似依赖人工（needs_confirmation）。

04 规则手册

全局部署并发上限

同时运行的部署任务不得超过 2 个，超出时新任务排队等待。 源码位置：core/deploy_executor.py:47（ThreadPoolExecutor(max_workers=2)）。 命中后果：新任务不会失败，而是留在 pending 直到有空位，运维可能误以为任务卡死。

07 入口点覆盖率

GET /api/nodes 运维在部署前查看主机台账，用来确认目标主机在线、组件安装状态是否正常。 输入是可选的分页参数，输出是主机列表含 IP、在线状态、组件清单。业务目的只有一个： 给部署动作提供目标选择的依据。失败边界是数据库不可用时返回空列表而非报错， 前端会误判为"没有主机"。
DELETE /api/nodes/{id} 主机下线后从台账移除，防止后续部署再选到已废弃的机器。 输入是主机 ID，输出是删除条数。业务目的是保持台账与实际集群一致，避免误部署。 失败边界是主机存在关联的历史部署任务时拒绝硬删，只做软删标记。
