# Phase 6：增量同步

只在用户明确说"代码改了，更新已有文档"时使用。前提：已经存在一份 Phase 1-3 生成的文档（及其 Phase 1 中间数据，如果还留着的话）。

这一步是痛点三"文档与代码脱节"的直接解法：目标是**只精确更新受影响的段落**，不改动没受影响的章节，从而让文档始终跟得上代码。codegraph（如已安装）能把"哪些代码改了"映射成"哪个文档章节该更新"。

## 步骤

1. 拿到 diff（`git diff <old_commit> <new_commit>`，或用户直接给的 diff）
2. **（推荐，装了 codegraph 时）先用 codegraph 把变更符号映射成影响面**：
   - 从 diff 里抽被改动的文件与符号（新增/删除/改动的类、函数、方法、字段），这些是"变更种子"。
   - 对这些种子跑 `impact`，得到受它们影响的符号/文件集合：
     ```bash
     node scripts/codegraph-extract.mjs impact --path <repo> <seed-symbol...>
     # 返回 { affected: [{ symbol, file, kind, depth }] }——被改动波及的下游调用者/引用者
     ```
   - 把 `impact` 命中的符号/文件，去映射到旧文档的"哪一段"（实体→领域模型+术语表，状态机→状态机章节，规则→规则手册）。`impact` 的 `depth` 越大追得越深，先 `--depth 2` 看直接波及，必要时加深。
3. 对 diff 中改动的文件（以及 impact 波及到的文件），逐一判断改动类型：
   - 实体/字段增删改（ORM 类、DDL 变更）→ 影响领域模型章节 + 术语表
   - 状态字段的赋值逻辑变化、新增/删除某个状态的赋值点 → 影响状态机章节（可用 `callers` 找状态迁移的触发方有没有一起变）
   - 条件表达式/阈值数值变化 → 影响规则手册章节
   - 新增/删除域间调用（新的 HTTP client 调用、新的消息生产/消费）→ 影响跨域链路文档
4. 只对受影响的章节重新执行对应的 Phase 1 提取 + Phase 2 整合，不要重跑全量
5. 生成一份"变更摘要"：哪些文档段落被更新了、依据是哪次代码变更（commit hash + 文件）——这个摘要本身也要交付给用户，方便他们快速 review 增量更新是否合理，而不是要求他们重新通读整份文档
6. 如果 diff 涉及的代码变更**看不出明确的业务含义**（比如只是重构，逻辑未变；或者变更影响不确定是否是业务逻辑变化），不要强行更新文档内容，标注"检测到相关代码变更，但未发现业务逻辑实质变化，如有出入请指出"

> **什么是 codegraph 在这里的真正价值**：不用 `impact` 的话，第 2-3 步靠人工看 diff + 全文搜符号来判断"这个改动该改哪个章节"，容易漏（改动在 A 方法里，但它被 B、C、D 调用，文档里 D 的流程也受影响；没有调用图就看不见）。`impact` 用代码调用图把这些"看不见的受影响方"精确定位出来，让增量更新不漏改、也不多改。这正是 codegraph 的强项（符号级调用图），也是它最适合的阶段。

## 何时建议全量重跑而不是增量

- 如果 diff 影响面过大（比如超过某个规模阈值，或涉及核心实体的结构性重构），增量更新的"只改受影响段落"假设可能不成立，主动向用户提示建议全量重跑一次 Phase 1-3，而不是硬套增量流程产出可能不一致的文档
- 装了 codegraph 但项目还**没建索引**（`probe` 显示 `indexed:false`）时，`impact` 无法用；要不要为增量临时建一座索引再 uninit，取决于项目规模与机器性能，说明清楚权衡后再决定，不要默默承担建索引成本
