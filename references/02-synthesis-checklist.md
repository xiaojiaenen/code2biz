# Phase 2：语义整合 —— 反空洞检查清单（R3/R4/R5/R6 集中实现）

Phase 1 产出的是结构化事实。这一阶段把事实组织成读得下去的文档。风险在于：LLM 生成文档天然倾向简洁、只写定义——这正是要解决的痛点。用下面的清单强制检查，**不是靠 prompt 里加一句"请详细一些"**。

## 全局配比：业务优先 70/30（R3 集中实现）

**每段内容都按"业务解读 ≥ 70% + 技术实现 ≤ 30%"** 写。"业务解读"包含：业务问题定义、真实使用场景、上下游业务联动、关键决策为什么这么选；"技术实现"是数据怎么存、调用链走什么、API 形状。

**自检**：随机抽 3 段，目测业务解读篇幅是否 ≥ 70%。如果某段技术细节（函数签名、ORM 字段类型）比业务动作（什么时候触发、谁会用、失败怎么处理）还多——这段就违反了 R3，需要重写。

---

## 每个核心概念（领域模型章节）必须包含

- [ ] **业务定义**（一句话讲清解决什么业务问题，不是"X 是一个表/类"）
- [ ] **真实场景举例**（不是"某个订单"，而是"订单号 SO20240815001，金额 ¥1,299，从『待支付』→『已支付』"这种具体到字段取值的例子）
- [ ] **为什么存在**（设计动机）：如果 Phase 1 提取到了 commit message / PR 描述 / 需求文档，引用；如果没有，明确写"设计动机未在代码中找到线索"，不要编
- [ ] **所有字段的业务含义**（来自 Phase 1 注释提取，缺注释的标"待确认"），按业务分组（不是按 ORM 字段顺序）
- [ ] **关键字段的取业务语义**：哪些是业务唯一键、哪些是状态字段、哪些是审计字段、哪些是预留
- [ ] **跨域叫法差异**（如果有）：同一个字段在不同域 / 不同仓库叫什么、对应的 UI 文案是什么

## 每条核心流程（核心流程章节）必须包含 —— 流程五维度（R5）

每条核心流程（部署主链路、下单链路、审批链路等）**必须覆盖以下五个维度**，缺一个就算空洞：

- [ ] **主流程**：从用户触发、接口调用、逻辑处理、数据存储、结果返回的完整业务链路，每一步对应什么业务动作、状态从什么变成什么、触发了什么副作用
- [ ] **分支流程**：不同业务条件、不同用户身份、不同场景下的分支处理逻辑及业务意义（"VIP 用户走快速通道"、"测试环境跳过实名校验"这类）
- [ ] **异常流程**：报错、超时、参数异常、权限不足、数据为空、空回执、网络中断、重试上限、补偿失败等场景的兜底逻辑，对应业务容错规则
  - **硬要求**：Phase 1 状态迁移表里有几条异常路径，文档里必须体现全部，不能挑 1-2 条意思一下
- [ ] **数据流转流程**：这条流程涉及的数据从产生、加工、传输、存储、更新、删除的全生命周期——数据在哪些表里、经过哪些缓存、被哪些服务读/写
- [ ] **权限 / 风控流程**：哪些业务节点需要权限校验、哪些场景有风控拦截、为什么这里需要拦截（不只是说"调用了 `check_permission`"，要说"防止误删已支付订单"）

**每一步的前置条件和后置条件**：哪些校验会阻止这一步发生；这一步失败会回退到什么状态、补偿逻辑是什么。

**涉及跨域调用**：标注调用的是哪个域 / 服务（结合 `08-domain-segmentation.md` 的域划分）。

## 整体架构章节必须包含 —— 架构拆解五问（R6）

整体架构章节是新人"看懂这个系统是怎么搭的"的主入口。**必答五问**：

- [ ] **架构拓扑**：分层架构 / 模块架构 / 服务架构（微服务/单体/组件化）完整结构，附一张顶层架构图（archify `architecture`）
- [ ] **设计目的**：为什么采用这个架构？适配的业务体量、业务迭代节奏、性能诉求、组织结构（康威定律）。如果代码里有架构决策记录（ADR / 注释），引用；没有则写"从代码结构推测，原因未找到文档线索"
- [ ] **各层 / 各模块职责**：每一层、每一个核心模块对应的业务能力、承载的场景——不是"用户服务负责用户"这种废话，而是"用户服务承载账号体系、登录态、企业组织树、权限组，这四个能力"
- [ ] **模块依赖关系**：模块之间怎么调用、数据怎么流转、业务怎么联动。结合 archify 依赖图 + R7 节点标注
- [ ] **架构优势、现存问题、业务适配性**：这套架构现在哪里跑得好、哪里已经吃力、未来业务扩张时哪里会成为瓶颈——这是给新人判断"这个系统还能扛多久"的关键

## 每条业务规则（规则手册章节）必须包含

- [ ] **规则的业务描述**（自然语言：什么时候、什么条件下、应该怎么处理、对应什么业务诉求）
- [ ] **原始数值边界**（直接来自 Phase 1 提取的条件表达式原文，**不要转述成模糊描述**——"约几秒"不如"30 秒"，"较多"不如"1000 条/次"）
- [ ] **违反 / 命中后的具体行为**（含业务后果："扣减失败则订单状态回退到『待支付』并发短信通知用户"——不是"扣减失败则报错"）
- [ ] **代码位置引用**（文件 + 函数/行号，可作为脚注 / 引用）
- [ ] **可调阈值类规则**必须配套**交互式计算器**（Phase 4）——读者输入数值立即看到命中哪条规则，而不是看一长串 if-else

## 术语表每一条必须包含 —— 术语三段式（R4）

- [ ] **字面定义**（标准技术/业务释义）
- [ ] **通俗白话**（非技术语言；让产品 / 业务人员能看懂）
- [ ] **业务场景绑定**（这个术语在当前项目具体业务里怎么体现、解决什么问题）
- [ ] **各域/各系统的实际叫法**（表名、字段名、UI 文案，来源不同就分别列出，跨域沟通鸡同鸭讲就是这里没做对）
- [ ] **字段枚举值映射**（比如不同系统 status 编码不一致，给出映射表；如 Node.status `online|offline|unknown` vs DeployTask.status `pending|running|success|failed|partial` vs License.status `inactive|active|expired`）

## 图谱 / 架构图配套（与 R7 一致）

- [ ] 每张 archify 图的**每个节点**必须有业务化标注（metadata.sublabel / context / tag，或节点旁的图注）
- [ ] 每张图下方必须有**业务解读**小节（200-400 字），把图里每个域 / 模块用一段话讲清楚业务定位、典型场景、异常处理
- [ ] 节点标注与业务解读小节**互相引用**（节点标号 / 名字与解读段落里的术语对得上）

## 全局检查

- [ ] 是否有任何一段文字是"Phase 1 没有对应结构化事实支撑"的？如果有，要么补做提取，要么明确标注为推测并降低表述的确定性语气（用"从代码结构推测"而不是断言）
- [ ] 是否所有数值（阈值、时间窗口、状态数量）都能对应到 Phase 1 提取的原始数据，而不是模型凭训练知识里"常见业务场景"脑补的数字
- [ ] **长度检查**：如果某个核心流程或核心实体的描述明显短于同级别的其他条目（比如其他流程都有 8-10 步，这个只有 2 步），先检查是不是 Phase 1 提取不完整，而不是直接接受这个偏短的结果
- [ ] **业务解读 vs 技术实现比例抽样 ≥ 7:3**（R3）
- [ ] **覆盖完整性**：所有入口点都有 `detailed` / `recorded` / `flagged` 三态之一的处理结论（R8 入口点完整性）

## 写作风格强制项

- [ ] 拒绝"如上图所示"、"具体可参考源码"、"详见接口文档"这类**伪引用**——要么给具体行号，要么给具体章节
- [ ] 拒绝"一般来说"、"通常情况下"——要么说"在当前项目中"并给出代码位置，要么不要写
- [ ] 区分**技术实现逻辑**和**业务规则逻辑**，分开讲，不能把"技术上怎么实现"和"业务上为什么这么做"混在一段
- [ ] 输出内容**全员可读**：技术开发、产品、测试、业务人员都能看懂——这意味着每个技术名词第一次出现时配通俗解释，之后可以直接用
